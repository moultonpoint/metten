# Maintainability standard

Make the next required change easy to locate, understand and verify. Apply this standard to features, bug fixes, refactors, tests, tooling and reviews. The product specification and accepted ADRs retain authority over behavior; this guide governs how to implement that behavior. It starts in Metten; adapting it elsewhere is separate work.

## Work recipe

1. **Locate ownership.** Start at the [code map](code-map.md), read the owning contract and relevant source/tests, and trace callers. Before editing, name the expected change path: authoritative state owner, affected inputs/outputs, and connected tests, fixtures, configuration and exports. For a bug, trace every caller of the changed function before editing. Done when the affected path and its required behavior are understood, including failure behavior and data preservation.
2. **Choose the smallest complete change.** Reuse the existing module or helper first, then standard facilities or installed dependencies. Keep ordinary changes local to their owner. An added module, interface, wrapper, dependency or configuration option must solve a named current requirement or demonstrated problem; explain that reason in the issue/PR. A concrete test need can justify an interface. Done when the change covers its callers and failures without speculative flexibility or unrelated cleanup.
3. **Implement and verify behavior.** Preserve validation, error handling, accessibility, durable state and existing safety controls when simplifying. Use the existing public interface with controlled inputs where possible. Nontrivial new behavior needs a focused meaningful check; bug fixes should reproduce the failure and show the correction. Where feasible, demonstrate that the regression check fails against the faulty behavior; otherwise state why and what evidence substitutes. Use internal checks when a resource or concurrency invariant cannot be established through the public interface. Follow [verification guidance](verification.md) for affected checks and evidence reuse. Done when the required evidence covers the actual changed behavior, with missing evidence stated plainly.
4. **Leave a short route for the next agent.** Update the owning contract when behavior changes and the map when entry points or maintained interfaces move. Put non-obvious reasons beside the code; use the existing glossary and ADR process for shared terminology or lasting architecture decisions. Keep one authoritative explanation and link to it. Done when another agent can find the owner, understand the promises and locate the right check without this conversation.

Use the issue/PR's existing summary to record these results. A small change needs a short explanation, not a new design document. Completion/review evidence is described in [verification guidance](verification.md#maintainability-review).

## Design decisions

- **Ownership:** each mutable fact has one authoritative owner. Other modules request changes or consume derived state; they do not maintain competing truth. Module ownership can be separate from the task that performs network I/O.
- **Locality:** keep provider formats/library types inside their adapter, strategy conditions in validated JSON, financial decisions in the shared engine and display behavior in the interface, following [ADR 0001](../adr/0001-rust-engine-and-tauri-boundaries.md). A cross-cutting capability extension can legitimately affect several owners; name why rather than adding forwarding layers to hide the edits.
- **Interfaces:** expose the smallest useful surface and hide implementation choices. Start with concrete Rust modules. Introduce shared interfaces where implementations or tests actually vary, or another current requirement needs one. Compare added structure with extending the existing owner directly; record the concrete advantage when the choice is consequential. Retain adapters that isolate real provider, storage, platform or security differences.
- **Readability:** use domain names and direct control flow. Keep distinct responsibilities understandable; split a file when that improves ownership or navigation, not to meet an arbitrary line count. Fewer lines, files, traits or test cases alone do not prove simplicity.
- **Performance:** optimize a measured bottleneck or a required capacity constraint. Reuse a reproducible measurement path and record its assumptions. Preserve meaningful resource proofs and hardware checks; a sample benchmark does not replace them. Proposed numbers remain proposals until validated.

For streaming/concurrent work, the owning design must specify required event ordering and loss policy, queue size/age bounds and overload response, freshness/invalidation, reconnect behavior, cancellation safety and shutdown ownership. Required observations and latest screen state have different delivery needs. Define who stops retries, waits for owned tasks and handles partial or non-cancelable work. Add focused failure checks where these behaviors change. This is a design checklist, not approval of a particular issue #5 mechanism or threshold.

Consult primary guidance when the change depends on language/runtime behavior: [Rust API future-proofing](https://rust-lang.github.io/api-guidelines/future-proofing.html), [Tokio channels](https://tokio.rs/tokio/tutorial/channels), [cancellation safety](https://docs.rs/tokio/latest/tokio/macro.select.html#cancellation-safety) and [graceful shutdown](https://tokio.rs/tokio/topics/shutdown). Check the relevant installed version when implementing. These references explain mechanisms; they do not prove Metten's correctness or performance.

## Test ordinary changes on paper

| Requested change | Expected owner and evidence |
| --- | --- |
| Provider renames a wire field | That provider's decoder and fixture; engine decisions keep consuming the same validated meaning. Provider integration is planned work. |
| Connection adds a failure reason | Owning state/error, affected response mapping and presentation check; no second state owner. |
| Supported strategy threshold changes | New validated JSON strategy version and relevant validation/evaluation evidence; existing engine arithmetic stays reusable. |
| New input or operator is supported | Explicit engine capability extension, schema/reference and affected tests; identify the legitimate wider impact. |
| Recording fails during a requested action | Storage/engine owner preserves confirmed state and exposes failure; desktop/UI checks show the actual outcome. |

If the actual change path exceeds the expected one, inspect and explain the cause before expanding it. Shared protocol types, validation, generated explanations and their tests may legitimately change together; fewer edited files is not the goal. Simplify within the approved scope when necessary; record larger work as a separate bounded issue. Evidence of difficulty, rather than aesthetic preference, justifies a refactor.

## Adoption and existing-code review

1. Publish this guide and its entry pointers through normal review. Once published, use it for each subsequent programming task and review; it does not depend on a personal skill being installed.
2. Use [review issue #43](https://github.com/moultonpoint/metten/issues/43) for one read-only review against a fixed source revision. Inventory maintained ownership using the code map and existing coverage map; inspect real change paths and report coverage gaps. Existing documentation drift reports are useful inputs but do not establish changeability.
3. For each demonstrated obstacle, record the source location, a realistic change it complicates, the smallest proposed correction and affected checks. Separate necessary safety/resource complexity from avoidable complexity. Make each accepted correction its own bounded issue; the review itself changes no application code.
4. After this guide and its AGENTS.md pointer are merged to the default branch, use the next three programming issues started afterward and followed to completion. The implementing agent records its expected change path before editing in the existing work summary. In each issue/PR record, the reviewer follows the published pointers to the actual owner/contract/check and compares the final edits with that path. Broken routes and unexplained departures are gaps; legitimate exceptions need requirement/source evidence. Reuse issue/PR evidence. In the third issue's completion record, the lead links all three and records one disposition: retain the standard or correct the observed instruction gaps. Missing evidence means not evaluated. This trial is separate from #43's audit acceptance. No recurring report, new score system or automated architecture gate is required.

The implementing agent maintains affected navigation and contracts; the reviewer checks them; the lead owns publication and the adoption follow-through. Reviewers should request corrections when a change creates a concrete maintenance obstacle or misses this recipe's evidence. Use existing review and required checks; architectural judgement remains review work. If a required check or concrete review objection is unresolved, report that limit rather than claiming completion. A pointer in AGENTS.md makes the standard discoverable; only subsequent task evidence establishes whether agents actually followed it. Longer-term, record a new review issue when repeated change difficulties demonstrate a need rather than scheduling speculative repository rewrites.
