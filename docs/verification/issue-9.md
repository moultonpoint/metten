# Issue #9 evidence: checkpoints and purchasing safety through feed interruptions

## Current evidence index

**Baseline.** Branch `feat/9-feed-interruptions` from published `main` `55e5c9cb5f441bab10ba336fa097bef104aceea9` (remote re-queried 2026-11-24T04:06Z and at delivery, unchanged). This record reflects review rounds 1 and 2 corrections on PR #79. Approved scope and owner decisions: [issue #9 start comment](https://github.com/moultonpoint/metten/issues/9). Behaviour contract: [engine feed-interruption section](../../crates/engine/src/README.md#feed-interruptions-issue-9).

**What changed.** (1) Kalshi loss blocks purchases through its own count, `Fence::source_losses`, of losses that were admitted but not yet applied. Each applied loss removes only its own admission; Resume or a new run context resets the count. After every admitted loss is applied, a run continues in the same market without Resume once fresh evidence qualifies. (2) Late results are refused with non-fencing `stale_result` without consuming the ordinal: an Update whose every referenced binding (values and coverage) belongs to a retired scheduled market, Metadata for such a market, and an older-generation Book. A late *unverified* Metadata for a market already retired in the published context is classified at admission and not counted as a loss (see the one-input lag under Limits). (3) Defect found by test 4 and fixed: a market promoted late after a reconnect across its opening was recorded as participating; entry now needs its exact-opening boundary in the applied batch.

## Limits

- The engine has no timers. Deadlines, expiry, boundaries and rollover advance only when the caller supplies inputs; the packaged clock is synthetic (20×). A real sleep/wake or clock-change detector is not part of this evidence.
- Native feed handling (decoder, intake, gap/overload revocation) and engine recovery are evidenced separately and never joined: the live feed is not connected to paper runs.
- A feed loss that lands while any request is in flight, including the user's own Pause, stops the run and discards the market. No order is dispatched after the loss is admitted. If the dispatch marker had already committed, that one authorised order is still sent once. The tests cover a loss before any dispatch and between intent and marker, not after the marker.
- A large clock jump is processed in one pass while holding the recorder; Pause still fences at once, but other requests may see `busy` meanwhile. Duration is unmeasured.
- A level checkpoint true in the fresh post-reconnect snapshot can latch from it (treated as observed now, not inferred during the gap).
- A book received after reconnect but before metadata reverification may buy once metadata is reverified, if it is still valid, never spent and matches the evaluated ask (all of it post-reconnect evidence).
- Retirement is published with each reply's context, so admission sees the retirement state after the last completed input. A late unverified result for a market that the in-flight input is itself retiring is still counted as a loss. Because a request is in flight, that stops the run (fails closed). This is the same known limit as any loss landing mid-request.
- Coinbase misses a skipped trade ID once a later trade advances its watermark; Kraken has no gap detection. Both sources are display-only; the owner accepted this limit for #9.
- No paper result proves live acceptance or fills.

## Corrections to the reviewed plan found during implementation

- An older-generation Book under the current context was already refused non-fatally (`range`, from `Input::canonical`), not fatal; it is now `stale_result`. A newer generation keeps `range`, which is non-fatal today.
- Unverified current metadata surfaces in the market receipt as `objective_blocked`, not `unverified_metadata`.
- The suspected participation defect (test 4) was real and is fixed in `paper.rs:Run::input`.
- Round 1: the boolean `source_lost` let one applied loss clear another's admission. It is now a count. The replay clear was unreachable (an applied revocation always changes the book token and generation) and is removed. A late unverified retired Metadata was counted as a loss at admission, and is now classified there. The stale classifier ignored coverage facts, and now checks them.
